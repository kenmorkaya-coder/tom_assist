# Executive Summary
Tom Assist is a separate desktop product that overlays ToM’s structural continuity capability onto the LLM web subscriptions people already use. The first build is Mac-first and uses ChatGPT in a Chromium browser. It does not replace the provider interface, collect provider credentials, require a metered LLM API, or modify the existing tom_owner application.
The app inserts a local, user-controlled continuity layer between a long-running project and the provider conversation. It captures visible turns, associates them with an explicit project, maintains an authoritative structural state outside the LLM, retrieves only context that remains relevant to the current reasoning state, prepares a compact continuity packet before submission, evaluates the returned answer for drift, and commits only verified state transitions.

Core product propositionTom Assist does not sell “more memory.” It preserves decision topology: objectives, binding constraints, accepted conclusions, rejected paths, completed work, unresolved dependencies, evidence and supersession history. It checks whether each continuation remains structurally consistent with what the project has already learned.

The primary empirical foundation is the completed paper “Eliminating Context Rot in Frozen LLMs: A Three-Mode Structural State-Coupling Architecture” [R1]. On frozen Gemma 4 26B at approximately 64K tokens, the paper separates three protection mechanisms: branch-conditioned resonance retrieval, an authoritative-state prelude with explicit precedence/anti-enumeration instructions, and per-expert MoE logit bias. The FULL condition reached 20/20 across two independently-authored 10-case pools; Layer 1 also rescued forced context removal from 1/40 baseline to 40/40. These results determine the app’s coupling surfaces, but not all three are available in a closed consumer subscription. Tom Assist Subscription Companion Mode can implement the first two surfaces and must separately validate their transfer to ChatGPT/other provider web sessions; direct expert bias is reserved for an optional governed-model mode where the model exposes router control.
The app cannot inspect or block the provider’s hidden decoding pipeline. In subscription mode, it can govern what the user sends, observe what the provider displays, warn about structural conflicts, prepare corrections and refuse to commit contradictory output into authoritative state. Direct pre-release control of generated tokens belongs to a future provider/API integration and is explicitly outside the first build.

# 1. Product Definition
## 1.1 Product statement
Tom Assist is a local-first continuity supervisor for long-running LLM work. It attaches a normal provider web conversation to a durable ToM project state, then conditions each new turn on the project’s held decisions and unresolved structure.
## 1.2 What the product is
• A separate application. It shares ToM runtime services and schemas where appropriate but does not inherit tom_owner’s interface, administrative purpose or repository architecture.
• A subscription companion. The user continues to work in ChatGPT, Claude or another supported web subscription. The first adapter targets ChatGPT web.
• A structural state authority. Project state is held outside the LLM and survives transcript truncation, new chats, application restarts and provider model changes.
• A context admission system. Context is selected for structural relevance, not simply recency or text similarity.
• A continuity verifier. The app identifies contradictions, revived rejected paths, dropped constraints, repeated completed work and objective drift.
• A user-controlled system. Injected text is previewable; state commits are inspectable and reversible; no hidden prompt submission is permitted.
## 1.3 What the product is not
• Not a fork or modification of tom_owner.
• Not a replacement chat model or consumer LLM service.
• Not a requirement for users to purchase API tokens.
• Not a generic transcript summariser.
• Not a credential-harvesting wrapper around provider accounts.
• Not an automation that calls undocumented provider endpoints.
• Not a claim of universal context-rot elimination in unrestricted conversations.
• Not direct MoE/attention routing inside a closed provider model.
## 1.4 Product success definition
The internal alpha succeeds when the same long-running ToM project can move across multiple ChatGPT browser sessions without losing held conclusions, constraints, rejected approaches, completed work or unresolved dependencies; when Tom Assist supplies the relevant state before each new turn; and when the live response is checked before it is allowed to alter authoritative project state.
# 2. Evidence Foundation and Claim Boundaries
## 2.1 Primary three-mode context-rot paper
The primary technical reference is “Eliminating Context Rot in Frozen LLMs: A Three-Mode Structural State-Coupling Architecture” [R1]. It wires SICD to a frozen off-the-shelf Gemma 4 26B through three shallow coupling surfaces: (1) branch-conditioned resonance retrieval from prior conversation turns, (2) an authoritative-state prompt prelude with explicit precedence and anti-enumeration instruction, and (3) inference-time per-expert MoE logit bias. No LLM fine-tuning, training signal or weight updates are used.

Scope boundaries

Product claims stay bounded; naturalistic cross-session and closed-provider validation is mandatory before consumer claims.
Semantic scope of the paper benchmark
The frozen-LLM benchmark primarily scores planted value recall (for example material, rate, year, diagnosis) under truncation and long-context pressure. It does not directly test persistence of concepts, goals, decision rationale or multi-object project topology.
Tom Assist shall not treat concept/goal continuity as already proven by [R1]. It shall implement these as typed structural objects and certify transfer separately on an action-consistency battery before claiming that broader capability.

Evidence boundaryThe app may cite [R1] as evidence that the three-mode SICD coupling eliminated the three tested failure classes on frozen Gemma 4 26B under the paper’s benchmark. It may also cite [R2] for the earlier 4,800-turn structural-retrieval calibration. It may not claim that Tom Assist on a closed subscription provider is the paper’s FULL condition: subscription mode has no Layer 2 router access. Any ChatGPT/Claude consumer claim must be earned by the app validation programme.

## 2.2 Paper-to-product translation
Tom Assist is not a literal copy of the paper runner. The paper proves a coupling pattern. The app must preserve the causal roles of the three surfaces while adapting them to provider capabilities. In Subscription Companion Mode, Layer 1 becomes the local structural context-admission engine and the state-block prelude becomes a visible, user-approved TOM_ASSIST_STATE block placed immediately before the current request. Layer 2 cannot be implemented against a closed provider web subscription because the app cannot access the provider’s MoE router or hidden logits. The architecture therefore exposes a model-coupling capability interface but reports expert_bias=false for ChatGPT web. A future local/open-model deployment can enable the full three-mode path without changing the continuity control plane.

## 2.5 Architectural lessons imported from the paper
The paper changes this specification in four material ways. First, the structural state itself - not the current user text - is the retrieval query. Second, retrieved material must be rendered as typed authoritative state rather than narrative recollection. Third, the layers cannot be assumed additive: [R1] directly observed negative composition interference under a prose prelude, so every layer combination requires paired validation. Fourth, model-internal biasing is a separate capability from memory/context admission and must be negotiated explicitly rather than implied by the browser overlay.
# 3. Context-Rot Failure Model
## 3.1 Failure classes
ID
Failure class
Description
App response
CR-1
Context-removal rot
A prior conversation fact/decision falls outside the provider-visible history or becomes unavailable after a new chat/session.
Layer-1-style structural anchor retrieval from the local conversation store; re-admit only the structurally relevant state.
CR-2
Enumeration-loop / prompt-surface rot
Retrieved facts are present but narrative framing causes the model to enumerate history instead of using the relevant state.
Typed TOM_ASSIST_STATE block, explicit precedence and anti-enumeration instruction; prose prelude retained only as an ablation.
CR-3
Attention/decoder degradation rot
Long-context decoding ignores relevant state or enters pathological low-probability routes.
Subscription mode can only reduce context pressure and restate authoritative state. Direct Layer 2 expert bias is available only in governed/local models with router access.
CR-4
Context-selection drift
Text-similar, recent or salient material is inserted even though it is stale, superseded or structurally irrelevant.
Branch/motif-conditioned candidate scoring, authority/supersession gates, stale penalties and bounded packet budget.
CR-5
Decision-topology decay
The system recalls a conclusion but loses why it was accepted, what it superseded or which dependencies remain open.
Typed state objects and explicit supports/depends_on/supersedes edges.
CR-6
Project-boundary contamination
State from another project/workstream enters the current prompt.
Hard project/workstream scoping and wrong-project rejection before ranking.
CR-7
Completion amnesia
Completed work is proposed again as if unresolved.
COMPLETED_WORK objects plus post-response COMPLETED_WORK_REPROPOSED intervention.
CR-8
Constraint erosion
A binding constraint disappears or is silently softened.
Constraint ledger, P0/P1 packet priority and CONSTRAINT_DROPPED intervention.
CR-9
Rejected-path revival
A ruled-out architecture/method returns without explicit reconsideration.
REJECTED_PATH guardrails and SUPERSEDED_PATH_REVIVED intervention.
CR-10
Illegitimate reversal
A conclusion changes without new evidence, explicit authority or a supersession record.
Mutation gate and explicit supersession transaction.

## 3.2 Operational definition of continuity
Continuity is not verbatim recall. A response preserves continuity when it remains compatible with the current objective, binding constraints, accepted conclusions, rejected paths, completed work, evidence status, unresolved dependencies and recorded supersession history.
continuity(response, project_state) =    preserves_objective  + preserves_binding_constraints  + respects_accepted_conclusions  + does_not_revive_rejected_paths_without_authority  + does_not_repeat_completed_work_as_open  + carries_unresolved_dependencies_forward  + cites_or_preserves_evidence status  + records legitimate supersession when decisions change
# 4. Scope, Non-Goals and Product Principles
## 4.1 First release scope
• macOS 14 or later on Apple Silicon.
• Chromium-based browser extension using Manifest V3.
• ChatGPT web provider adapter as the first supported surface.
• One active Tom Assist project per browser tab; multiple projects supported overall.
• Local-only storage and processing by default.
• No mandatory provider API and no external LLM API.
• Visible context-packet preview before submission.
• Post-response continuity evaluation and candidate state-change review.
• Project export, import, snapshot and cold-restart recovery.
## 4.2 Explicit non-goals for the internal alpha
• Native iOS overlay of third-party LLM apps.
• Direct access to provider hidden system prompts, KV cache, logits, attention or model weights.
• Automatic capture from native provider desktop applications.
• Unattended autonomous message submission.
• Cloud account sync, team collaboration or consumer billing.
• Direct modification of tom_owner.
• Universal cross-provider compatibility.
• Automatic acceptance of LLM-generated state mutations.

## 5.3 Primary workflow: governed prompt preparation
1. User selects/attaches a Tom Assist project to the browser tab.2. User writes a normal prompt in the provider composer.3. On submit, the extension pauses the event for local preparation.4. The local service sends the prompt to the ToM adapter as a non-authoritative load.5. ToM activates relevant branches/motifs and ranks context candidates.6. The service builds a compact ContinuityPacket within the configured token budget.7. The extension shows a preview: included items, exclusions, warnings and token cost.8. User approves, edits, bypasses once or cancels.9. The extension inserts the packet into the visible provider composer and resumes the normal submit.10. The provider generates under the user’s existing subscription.
## 5.4 Primary workflow: response evaluation and state commit
1. The provider adapter observes streaming and waits for response completion.2. The visible response is ingested as evidence, not authoritative state.3. The continuity engine checks it against held project state.4. The UI displays PASS, REVIEW or CONFLICT with evidence links.5. Candidate state mutations are generated by approved extraction channels.6. ToM checks candidate mutations for contradiction, authority and supersession.7. User accepts, edits or rejects each mutation.8. Accepted mutations are committed to the event log and ToM state.9. A snapshot may be created according to policy.

## 6.3 Native Messaging and local IPC boundary
Chrome Native Messaging remains the recommended extension-to-device boundary because it avoids a generally reachable localhost service. The native host is deliberately thin: it authenticates the extension ID, validates protocol/schema size, forwards one correlated envelope to a user-only Unix-domain socket and returns the response. tom-assistd owns every project decision. A development-only loopback transport may exist behind a build flag but is never the production default.

## 6.7 PREPARE_TURN transaction
Prompt preparation is a read/preview transaction until the user actually submits. This prevents a draft, cancelled message or provider DOM glitch from permanently deforming project state.
1  Extension captures the current draft and active project/workstream binding.2  tom-assistd opens PREPARE_TURN at authoritative state_version = V and ToM checkpoint = D.3  ToMAdapter.preview_activate(draft, D) computes current structural activation without permanent commit.4  ContextAdmissionEngine collects project-scoped ledger objects, recent discourse and historical anchors.5  Hard gates remove cross-project, superseded-positive, low-integrity and privacy-disallowed candidates.6  Remaining candidates are scored by structural resonance + semantic/dependency relevance + authority, with stale/conflict/redundancy penalties.7  BudgetController selects the smallest load-bearing set.8  AuthoritativeStateRenderer creates TOM_ASSIST_STATE and a packet_digest bound to V/D.9  Extension shows preview; the original user draft remains independently editable.10 On explicit Send with Tom, the visible state block + unchanged user draft are submitted and USER_TURN_SENT is appended idempotently.11 If state_version changed before send, the packet is invalidated and must be rebuilt.

## 6.8 Structural retrieval path
Layer-1-style retrieval is not query-text search with a Tom score appended. The current structural state is the primary query. Candidate turns/anchors retain the structural snapshot/signature under which they were emitted. The app asks which prior anchors resonate with the branches/motifs activated by the current draft and project state, then fuses that structural score with bounded semantic/dependency signals. The earlier w_leaf=0.6 result remains a calibration prior from [R2]/[R1], not a hard-coded production constant.
candidate_score =    structural_resonance(policy_version)  + semantic_relevance  + dependency_relevance  + authority_strength  + bounded_recency  - stale_penalty  - supersession_penalty  - contradiction_penalty  - redundancy_penaltyHard gates execute before scoring. A high score can never resurrect a cross-project item or a superseded positive state as current truth.
## 6.9 Authoritative-state block architecture
The paper’s state-block result is treated as an architecture requirement. Tom Assist therefore renders typed state, not a narrative summary. The current user request remains the highest authority: if it explicitly conflicts with held state, the provider is told to treat the conflict as a proposed change/reopening rather than silently following old state or silently overwriting it.

### 6.9.1 Subscription Companion Mode is a primary architecture, not a degraded fallback
Tom Assist must be useful on closed consumer subscriptions even when the provider exposes no expert-router hook. [R1] gives strong evidence for the accessible part of that architecture: under forced truncation, Layer 1 moved plant recall from 1/40 to 40/40; at approximately 64K tokens the pooled conditions were BASE 17/20, L1-prose 17/20, L1-state 19/20 and FULL 20/20. The engineering interpretation is not that Layer 1 equals FULL. It is that structural re-admission plus authoritative framing addresses a large and product-relevant class of state-access/state-selection failures, while Layer 2 closes a residual class where correct state is present but decoding still goes wrong.
Primary subscription turn path:
current user draft  -> ToM preview activation against durable project state  -> retrieve typed structural objects + minimum supporting anchors  -> apply hard scope/authority/supersession gates  -> render authoritative TOM_ASSIST_STATE  -> submit unchanged user request through the existing subscription  -> capture provider response  -> evaluate response against the same state/packet lineage  -> propose corrections/state mutations  -> commit only through explicit authority gate
For the initial product, success therefore means preventing project-state regression: forgotten goals, dropped constraints, revived rejected paths, repeated completed work, lost dependencies, stale definitions and silent reversal of held decisions. These are the failures the subscription architecture is designed to attack directly. Layer 2 remains an optional ceiling-raising mechanism for governed/open models; it is not a prerequisite for the consumer product.
Evidence boundary: [R1] directly proves planted-fact rescue and three-mode complementarity on its benchmark. The expected high utility for richer project state is an application hypothesis and is subject to Gate G16; this specification does not promote that hypothesis into a paper-proven claim.
### 6.9.2 Retrieval targets are structural objects, not fact records
The production retrieval unit is a typed state object or a provenance-bearing anchor, not a generic “fact”. Facts are only one possible evidence payload. A long-running project is primarily held together by relationships among concepts, goals, constraints, decisions, rejected alternatives, completed work and unresolved dependencies. Tom Assist shall preserve those relationships outside the LLM and select the smallest load-bearing subset for each turn.

### 6.9.3 Concept and goal continuity packet composition
Packet assembly should preserve topology, not merely a list of remembered statements. The renderer therefore emits current objects in an order that mirrors decision authority and task dependence:

The packet budget controller is relationship-aware. If a decision depends on a concept definition and a hard constraint, evicting either supporting object can make the decision meaningless even if the decision text itself remains. Candidate selection therefore operates on connected state subgraphs or dependency-closed object bundles when necessary, rather than independently ranking every sentence.

## 6.10 EVALUATE_TURN transaction and response authority
The provider response is captured as untrusted observation. It is evaluated against the same state lineage that produced the outgoing packet. Provider text may create mutation candidates, but it may not directly commit a decision, constraint, completed-work marker, evidence status or permanent ToM learning state.
1  Extension buffers streaming fragments and emits ASSISTANT_TURN_COMPLETE only after stable completion.2  Raw response is appended to the immutable conversation store with content hash and packet_digest linkage.3  GovernanceEngine evaluates response against state_version V and the exact admitted candidate set.4  ToMAdapter may perform read-only/shadow activation for conflict and structural-fit analysis.5  Engine emits PASS / REVIEW / CONFLICT / INCOMPLETE plus evidence-linked interventions.6  Semantic extraction produces StateMutationCandidate objects only.7  User/verified ToM authority chooses accept, reject, edit, supersede or reopen.8  COMMIT_STATE uses compare-and-swap on state_version. ## 6.11 Project, workstream, session and fork model
A Tom Assist project can bind many provider conversations. Workstreams prevent unrelated objectives from contaminating one another. A provider conversation is represented as a session branch with parent lineage, not as the project itself. Starting a new ChatGPT chat while remaining on the same workstream intentionally tests/contextualises CR-1: the provider starts with little/no old history while Tom Assist re-admits the required state. If two chats diverge, each session records the state_version from which it forked; project-global commits can be merged only through an explicit reconciliation/supersession operation.

## 6.12 Concurrency, idempotency and crash consistency
All mutating calls carry project_id, base_state_version and idempotency_key. State commits use a single-writer logical transaction per project; reads may run concurrently on immutable snapshots. PREPARE_TURN returns packet_digest = hash(project_id, workstream_id, state_version, tom_checkpoint_digest, admitted_item_ids, renderer_version, user_draft_hash). A send/evaluation associated with a different digest is marked stale. SQLite WAL plus an append-only event journal must make a committed event recoverable after process/browser crashes.
## 6.13 Trust boundaries and prompt-injection resistance
Tom Assist has three trust classes: locally committed authoritative state, user-originated current intent, and untrusted provider/page content. A page can display text that looks like a TOM_ASSIST_STATE block, but only blocks carrying a local packet_digest in the extension/service transaction are trusted by Tom Assist. Provider responses cannot promote their own claims into the ledger. The extension never exports cookies, passwords or hidden session tokens; it reads only user-visible conversation content and writes only to the visible composer after user approval.

## 6.14 Degraded operation and fail-safe behaviour
The continuity service fails closed for state mutation and fail-visible for conversation use. If ToM or the database is unavailable, capture may continue into a bounded local queue but no new authoritative commit is allowed. The user may explicitly send without Tom after a warning. If the provider adapter is broken, Tom Assist detaches interception rather than guessing selectors. If only semantic extraction is unavailable, manual structured capture and deterministic authority remain operational.
## 6.15 Layer 2 governed-model interface
A future governed/local model adapter may implement the paper’s Layer 2 without changing the app’s state, retrieval or UI architecture. The adapter receives a structurally-derived bias request plus the current ToM snapshot. For a Gemma-compatible MoE implementation, [R1] computed stress-weighted L/S/T axis proportions, mapped them across expert chunks, zero-centred the bias and applied alpha=1.0 before top-k expert selection. These exact values/mapping are a reproducibility profile for the paper, not a universal Tom Assist default. Production adapters must declare their own expert topology and pass non-inferiority/ablation gates.

Production scoring must be recalibrated against the current ToM runtime and logged by policy_version; no historical scalar is allowed to become an unexplained constant.

## 11.6 Token-budget policy
CTX-001 The default internal packet budget shall be configurable and initially capped at approximately 1,200 estimated tokens, excluding the user draft.
CTX-002 The packet builder shall prioritise hard constraints and guardrails before descriptive background.
CTX-003 The preview shall show estimated token overhead and allow the user to expand or compact sections.
CTX-004 Context packet history shall be stored with candidate IDs, scores, exclusions and policy version.
CTX-005 The packet budget controller shall treat binding constraints, current objective and active guardrails as non-evictable before optional background anchors.
CTX-006 Production rendering shall use the authoritative-state format. A prose “Earlier in this conversation...” renderer exists only for controlled ablation/diagnostics.
CTX-007 The state renderer shall preserve the user draft verbatim outside the generated state block; editing the state block shall never silently alter the user request.
CTX-008 Context retrieval shall support typed CONCEPT and OBJECTIVE/GOAL objects as first-class candidates; fact/evidence anchors shall not be the only retrieval unit.
CTX-009 When a selected state object depends on other objects required to interpret it correctly, the budget controller shall admit a dependency-closed minimal bundle or explicitly mark the missing dependency.
CTX-010 Canonical state objects shall outrank duplicate raw-turn paraphrases for continuity rendering; raw turns remain provenance/evidence unless no canonical state exists.
CTX-011 Concept refinements and objective changes shall be represented through explicit version/supersession/reopen lineage; retrieval shall never silently merge incompatible definitions or goals.
CTX-012 Subscription Companion Mode shall be validated and releasable without Layer 2. Lack of provider router access shall not disable Layer 1, authoritative-state framing or post-response governance.

## 12.1 Response evaluation states

Meaning

## 12.4 Authority and blocking behaviour
In Subscription Companion Mode, Tom Assist cannot prevent the provider from displaying its answer. “Blocking” means blocking the answer from altering authoritative Tom Assist state and blocking automatic continuation under an unacknowledged conflict. The user can still read, copy or use the provider response.
## 12.5 User correction workflow
• Accept Tom’s conflict and generate a corrective next prompt.
• Mark the response as a legitimate decision change and complete the supersession form.
• Dismiss as irrelevant for this turn without changing the underlying state.
• Mark as false positive, recording the category and reason for calibration.
• Edit the conflicting state object when the ledger itself is wrong.

## 14.3 Idempotency and concurrency
All mutations are optimistic-concurrency controlled using expected_state_version. # 18. Validation Programme and Acceptance Gates
## 18.1 Experimental arms
Arm
Condition
SUB-A
Base provider subscription conversation without Tom Assist.
SUB-B
Conventional recent-history/summary or text-semantic retrieval baseline.
SUB-C
Tom Assist structural retrieval rendered as prose prelude - diagnostic ablation mirroring the failure-prone paper format.
SUB-D
Tom Assist production Subscription Companion Mode: current ToM structural state retrieves typed project objects and supporting anchors; an authoritative TOM_ASSIST_STATE block carries concepts, goals/objectives, decisions, constraints, rejected paths, completed work, dependencies, evidence boundaries and supersessions; post-response governance checks continuity. SUB-E

## 18.2 Test corpus
• Historical real-work replay. Selected ToM/SICD conversations with known regressions and decision boundaries.
• Frozen deterministic battery. Synthetic but hand-audited project histories covering every intervention class.
• Adversarial paraphrase battery. Revive rejected paths using different language; distract with lexically similar but structurally irrelevant content.
• Cross-session battery. Continue after new chat, transcript truncation, browser restart and cold service restart.
• Legitimate reversal battery. Supply new evidence and test whether the system permits explicit supersession rather than blocking all change.
• Wrong/stale-state ablations. Feed state from another project or freeze state updates to establish causal dependence.
### 18.2.1 Typed structural-continuity battery
The app must prove the transfer from planted-fact recall to the actual objects required by project work. Build a frozen battery of 100-300-turn histories in which the load-bearing state is deliberately distributed across time and later subjected to drift, paraphrase, distraction, truncation, new-chat continuation and legitimate revision.
• Plant at least one canonical CONCEPT definition/mechanism, one active OBJECTIVE/GOAL, one hard CONSTRAINT, one accepted DECISION, one REJECTED_PATH, one COMPLETED_WORK result, one UNRESOLVED_DEPENDENCY and one EVIDENCE/ASSUMPTION boundary per scenario family.
• Include supersession cases: a held decision or concept is deliberately refined/replaced later. Success requires using the new state while preserving the prior state as auditable history.
• Score action consistency, not mere repetition. Questions should require choosing a next step, rejecting an invalid proposal, combining a goal with constraints, respecting a dependency, or explaining why a superseded/rejected path is no longer current.
• Run SUB-A through SUB-E on identical histories. SUB-B provides the conventional summary/text-semantic retrieval baseline; SUB-E provides the wrong/stale-structural-state causal ablation.
• Report each object family separately and as a pre-registered aggregate. A single strong fact-recall score cannot compensate for collapse on concepts, goals, constraints or relationship fidelity.
• Include no-rot controls where all required state is already short and visible. Tom Assist must remain non-inferior and avoid gratuitous packet injection.
Primary hypothesis for Subscription Companion Mode: when long-horizon state is unavailable, stale or structurally diluted in the provider session, SUB-D preserves project-level action consistency materially better than both the unaided subscription and a conventional text/summary baseline. This hypothesis is earned only if G16 passes.

## 18.5 Paper-replication relationship

## 21.3 Decisive falsifiers
• Tom Assist does not reduce stale-context injection relative to a strong summary/retrieval baseline on held-out live sessions.
• Wrong or stale ToM state performs as well as live correct state, indicating the structural state is not causally contributing.
• False blocking of legitimate decision change remains above the acceptance threshold after calibration.
• The packet’s token/latency overhead erases the continuity benefit in normal work.
• Provider adapter instability makes capture incomplete enough to corrupt project state.
• User-confirmed state cannot be recovered exactly after cold restart and migration.

• Team workspaces with explicit ownership and decision authority.
• Tomarium visualisation as an optional view of structural project state, not the core product.
Tomarium should remain an optional visualisation of the living project state. It is not a substitute for the continuity ledger, evidence links or governance workflow.
## 22.2 Governed/open-model full three-mode mode
This mode exposes an inference gateway for models whose router or decoding surface is controllable. It reuses the same project state, anchor store, context-admission engine and authoritative-state renderer, then optionally adds the [R1] Layer 2 expert-bias hook. This is the architectural route for reproducing the paper’s FULL condition; it is not represented as a capability of ordinary ChatGPT/Claude browser subscriptions.
## 22.3 Research extensions
• Replicate the Layer 2 expert-bias result across a second model family, additional context scales and naturalistic long-form conversations before treating it as a general model-coupling capability.
• ToM-native unrestricted-language ingestion after held-out paraphrase, nuisance and contradiction certification.
• Cross-project structural transfer with explicit shared evidence and no accidental contamination.
• Automated authority promotion only after precision, false-intervention and causal-ablation thresholds are met.

## D.2 Glossary
Term
Definition
Authoritative state
Project state accepted through a user/ToM verified commit, not merely stated by the provider.
Branch-conditioned retrieval
Retrieval conditioned on the ToM tree’s currently activated structural state rather than text similarity alone.
Candidate mutation
A proposed addition/change to state that has not passed the authority gate.
Context admission
The process that decides which project information is allowed into the next provider prompt.
Context-selection drift
Admission of plausible but stale or structurally irrelevant context during prompt assembly.
Continuity packet
Compact, visible context injected into the outgoing provider message to preserve project state.
Decision topology
The graph of decisions, reasons, evidence, rejected alternatives, constraints and unresolved dependencies.
Provider adapter
Replaceable extension module that interacts with a supported provider’s rendered web UI.
Sequence-level interference
Loss of signal among competing long-range dependencies inside the model’s processing of a long prompt.
Subscription Companion Mode
Tom Assist operates beside an existing web subscription without owning model inference.
Supersession
Explicit authorised replacement of prior state while preserving its history and reason.
ToM adapter
Versioned boundary between Tom Assist and the current ToM runtime.
Authoritative-state prelude
Typed TOM_ASSIST_STATE prompt block with precedence and anti-enumeration instruction, derived from the successful framing condition in [R1].
Context-removal rot
Prior conversation state becomes unavailable to the provider-visible prompt through truncation, new chat or window pressure.
Enumeration-loop rot
Long-context failure where the model enumerates/reconstructs history instead of using an already retrieved authoritative fact.
Governed Model Mode
Tom Assist deployment where the model inference surface is controllable and may expose Layer 2 expert/router biasing.
PREPARE_TURN
Snapshot-bound, non-mutating transaction that builds and previews a continuity/state packet for a draft.
EVALUATE_TURN
Post-response transaction that checks a completed provider response against the packet/state lineage and emits interventions/candidates.
packet_digest
Hash binding outgoing state_version, ToM checkpoint, selected items, renderer version and user draft; used to detect stale/mismatched evaluations.
